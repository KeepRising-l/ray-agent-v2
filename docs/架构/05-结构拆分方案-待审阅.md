## 1. 我们要解决什么问题？

现在要找“运行排队”“等待用户”或“文档重试”时，相关类分散在 `run` 和 `task`：

- `run` 下同时有容量、幂等、调度接口、等待用户、接口控制器和启动保护。
- `task` 里既有聊天运行队列，也有文档入库重试；任务页面又同时展示聊天和文档状态。
- 一个功能要跨多个包并不一定有问题，但目前包名不能直接帮助读者判断代码归属。

目标是让人先按**功能**找到入口，再在功能内按职责定位代码；是否新增 Maven 模块并非目标。目前保留 `ray-agent-runtime` 和 `ray-agent-server` 两个后端模块，不预先增加空模块或空接口。

## 3. 建议保留的项目整体结构

```text
ray-agent-v2/
├── ray-agent-web/              前端页面、组件和接口请求
├── ray-agent-runtime/          模型契约、Agent 循环、工具和上下文能力
└── ray-agent-server/           面向产品的接口、业务编排和持久化
    └── cn/ray/agent/server/
        ├── chat/               聊天入口、模式分派与工作流
        ├── conversation/       会话、消息、历史和摘要持久化
        ├── run/                一次聊天运行的准入、调度、等待与接口
        ├── task/               暂保留跨聊天和文档的任务视图、启动恢复
        ├── knowledge/          知识库、文档与原文件管理
        ├── rag/                文档解析、入库、检索、证据与回答
        ├── identity/           个人身份与认证
        ├── admin/              后台配置、审计与统计
        ├── model/              模型渠道及运行时配置
        └── tools/              网页、用户提问等具体工具
```

这张图只表示**当前建议的职责归属**。它不要求把所有 Controller、Service、Repository 拆进独立 Maven 模块；也没有确定 `chat`、`conversation`、`rag` 等包内部将来是否需要进一步整理。

## 4. 本次重点：run 和 task 建议如何分包

下面是建议的目标，除 `run.admission` 的五个类已提前移动外，其余均**尚未实施**。

```text
server/
├── run/
│   ├── admission/                    运行准入：当前五个类已提前迁入
│   │   ├── BoundedRunExecutor
│   │   ├── RunConcurrencyPolicy
│   │   ├── RequestIdempotencyService
│   │   ├── IdempotencyAdvice
│   │   └── SessionWriteLease
│   ├── dispatch/                     运行调度：建议
│   │   ├── RunDispatcher
│   │   ├── DirectRunDispatcher
│   │   ├── QueuedRunDispatcher       ← 目前在 task
│   │   ├── RunQueue                  ← 目前在 task
│   │   └── TaskStateRepository       ← 目前在 task
│   ├── question/                     用户提问与接续：建议
│   │   ├── PendingQuestionStore
│   │   └── RunResumeService
│   ├── api/                          运行相关 HTTP 入口：建议
│   │   ├── RunQueryController
│   │   ├── RunRecoveryController
│   │   └── UserAnswerController
│   └── RunStateService               暂留：单实例锁及启动协调
│
├── task/                             暂留跨功能任务视图
│   ├── TaskController
│   ├── TaskQueryService
│   └── InterruptedRunRecovery        暂留：同时恢复聊天和文档状态
│
└── rag/
    └── ingest/                       文档入库与重试：建议
        ├── DocumentIngestionService  已存在
        ├── DocumentReindexService    已存在
        ├── IngestionCheckpoint       已存在
        ├── RetryScheduler            ← 目前在 task
        └── TaskCheckpointStore       ← 目前在 task
```

### 4.1 run.admission：这次请求能不能进入？

**建议负责：**查重、检查容量、为本次 run 预留名额，以及创建 run 时的会话写入互斥。

**需要注意：**`BoundedRunExecutor` 虽已迁入 `admission`，它实际上也负责提交任务并持有队列、线程池。这个名字和位置是否足够清晰是一个**待讨论点**：可以先保留，也可以以后在理解其完整生命周期后考虑拆分准入与调度职责。不能仅凭文件夹名字就认定它只做准入。

### 4.2 run.dispatch：已接纳的 run 什么时候执行？

**建议负责：**`RunDispatcher` 定义调度入口，`QueuedRunDispatcher` 负责排队桥接，`RunQueue` 管理单进程 FIFO；`TaskStateRepository` 记录聊天 run 排队和开始执行的阶段。`DirectRunDispatcher` 是现有直接执行实现，是否继续保留应先检查使用场景和测试，不因分包顺便删除。

**为什么建议把它们放一起：**现在调度接口在 `run`，队列和排队实现放在 `task`；沿着一个请求查调度时需要来回切包。归到一起后，可以先从 `run.dispatch` 找运行调度。

**不是新 MQ：**这个建议只是归类现有代码，不改变当前单进程内存队列与数据库状态的关系。

### 4.3 run.question：需要用户补充后，如何接续？

**建议负责：**`PendingQuestionStore` 保存和消费问题及检查点；`RunResumeService` 负责支持场景的接续。接收 HTTP 回答的 `UserAnswerController` 放在下方 `run.api`，与内部接续逻辑分开。

**边界：**这是受支持的等待用户检查点，不代表任意断点恢复，也不意味着同一会话普通追问已经支持排队。

### 4.4 run.api：前端从哪里查询、取消或回答？

**建议负责：**集中保留 `RunQueryController`、`RunRecoveryController`、`UserAnswerController` 三个运行相关 HTTP 入口。入口与内部服务依然是 Java 包划分，不需要为了每个入口额外造一个接口。

接口地址、请求体、响应、SSE 与鉴权行为应保持现状；这里只提议类的位置。

### 4.5 task：为什么还留着？

- `TaskController` 和 `TaskQueryService` 不只是聊天运行页面：它们还查询文档任务和重试尝试，属于**跨功能的统一任务视图**，不适合直接整个搬入 `run`。
- `InterruptedRunRecovery` 当前同时调用聊天运行恢复和文档处理恢复，所以先保留在 `task`；以后如果要让启动恢复更清晰，可以单独讨论系统启动协调的位置。
- `RunStateService` 负责单实例锁和调用启动恢复，目前先留在 `run` 根包。它和 `InterruptedRunRecovery` 是否需要一个更明确的共同位置，等实际讨论启动流程再定。

### 4.6 rag.ingest：文档任务放哪里？

`RetryScheduler` 只处理符合条件的文档 Embedding 临时失败；`TaskCheckpointStore` 记录文档入库的尝试和阶段。它们的直接业务归属是文档入库，建议以后与 `DocumentIngestionService` 放在 `rag.ingest` 附近，避免看到 `task` 就以为它们是聊天队列的一部分。

迁移前仍需检查 `knowledge`、后台任务和测试引用；文档任务重试语义不应与聊天 run 接续混为一谈。

## 5. 怎么按功能找代码？

以“用户发送一条消息，需要等待执行槽”为例：

```text
chat/ChatController
  接收请求
      ↓
chat/ChatApplicationService
  组织请求、运行创建和流式返回
      ↓
run/admission
  检查幂等、会话写入和容量
      ↓
run/dispatch
  队列等待、取得执行槽、开始运行
      ↓
chat 的模式工作流 + runtime 的模型与工具能力
  执行回答；需要补充时进入 run/question
```

这条线是**建议分包后的阅读路线示意**，其中 `run.dispatch` 和 `run.question` 尚未建立。箭头表示业务阶段，异步或事件边界不一定是直接同步方法调用。

另外，一次 run 的配置快照当前在 `admin/RunSnapshotService`，会话和消息存储在 `conversation/ConversationRepository`。本次不建议只为了图上整齐就搬这些类；是否重新归属，需结合后台配置和会话职责另行讨论。
