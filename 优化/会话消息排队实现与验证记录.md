评审修订：[评审修订记录](会话消息排队设计-评审修订记录.md)  
分支：`Ray/structure-context-rag`（未提交、未推送）

## 1. 本次实现的目标

回答期间输入框保持可用；同会话消息按发送顺序排队，前一条结束后下一条才开始；不同会话仍并行。排队状态、取消和提示在前端可见，消息文本在服务端落库。

本期仍未做消息合并、刷新/断线续流、多实例队列。按设计第 11 节，每会话活动 run 默认上限 2，排队等待上限 120 秒。

## 2. 落地内容

### 2.1 数据库与准入

`V011__session_queue.sql`：

1. **删除旧的会话单活动 run 唯一索引** `ra_one_active_run`。这是实施时实际发现的阻塞：`V008` 建立的 partial unique index 会让第二条 `QUEUED` 直接触发 `DuplicateKeyException`，接口返回 500 而不是排队。
2. 新增 `ra_run_queue_seq` 序列与 `ra_run.queue_seq`，历史数据按 `created_at, id` 确定性回填，之后由数据库默认 `nextval` 分配。
3. `queue_seq` 最终为 `NOT NULL`，消息和运行列表按它排序，避免同一毫秒内的顺序歧义。

`ConversationRepository.begin()`：

- 删除“同会话已有活动 run 即 409”。
- `WAITING_USER` 仍返回 409，必须先回答或取消。
- 活动 run 数（`CREATED/QUEUED/RUNNING/WAITING_USER`）达到 `ray.run.max-queued-per-session`（默认 2）返回 429；因此默认形态是“1 条执行 + 1 条排队”，第三条会收到容量提示。
- 插入 run 时不再显式写 `queue_seq`。

### 2.2 调度与会话串行

- 新增 `SessionRunGate`：按会话记录持有者 runId，`tryEnter` 幂等（同一 run 可重入），`release` 只释放自己的锁。等待用户回答期间闸门仍由原 run 持有。
- `RunQueue` 改为泛型并支持比较器：按 `queue_seq` 插入等待区；`ready(Predicate)` 从队首跳过被闸门挡住的 job，避免队首阻塞其他会话。
- `BoundedRunExecutor`：
  - 提交时携带 session/run/queueSeq；准入阶段先 `enter` 占住会话闸门，落库早的运行不会被提交慢的 HTTP 线程抢先。
  - 线程池拒绝任务时调用 `onRejected`，随后释放闸门并关闭 permit。
  - `release` 释放闸门后唤醒等待区。
- `QueuedRunDispatcher` 启动失败时释放闸门；取消仍通过 `Permit.close()` 清理线程池占位。
- `PendingQuestionStore.expire()` 返回实际被结束的 `(owner, session, run)`，由 `ChatApplicationService` 释放闸门；`consume()` 不再内部调用过期扫描，过期回答返回 410。

### 2.3 超时与生命周期

- `ray.run.queue-timeout-ms` 停用；新增：
  - `ray.run.session-queue-timeout-ms=120000`：从准入到实际开始执行的排队上限，超时以 `QUEUE_TIMEOUT` 结束。
  - `ray.run.max-queued-per-session=2`：每会话活动 run 上限。
- SSE 超时改为“剩余运行预算 + 排队上限 + 5 秒”，覆盖排队与执行两段；`started()` 后再启动实际运行 deadline。
- `WAITING_USER` 结束时释放全局执行槽但保留会话闸门；回答、取消、过期分别释放。

### 2.4 前端多请求

`chatSession.js` 从“每会话一个 operation”改为“每个请求一个 operation”：

- key 为 `clientRequestId`，回答续跑为 `answer:<runId>:<questionId>`；同一请求重复调用直接返回。
- `newer()` 阻止旧请求覆盖错误、草稿和待确认记录；`leading()` 决定谁接管轨迹和状态栏，排队消息不会清掉正在显示的回答。
- `onMeta` 用 `clientRequestId` 把本地先行消息绑定到 `runId`；`onQueue` 区分“已排队”和“正在执行”，取得执行槽后才接管视图。
- `submit()` 的乐观消息带 `clientRequestId` 和空 `runId`；错误时只把最新失败请求放回输入框。
- 新增 `cancelQueued(runId)`；`cancel()` 优先取消运行中的 op，否则取最新带 runId 的 op 或活动 run。

`ChatWorkspace.vue` / `app.css`：

- 输入框不再因 `busy` 禁用；只在创建/读取、等待回答、结果未确认时禁用。
- 模型渠道在回答期间仍可切换（对下一条消息生效）。
- 输入框上方列出排队消息（顺序、文本、取消按钮）。

### 3.2 真实数据库迁移

在本机 PostgreSQL 容器核对：

- `ra_run.queue_seq` 存在，`NOT NULL`，默认 `nextval('ra_run_queue_seq')`。
- `ra_one_active_run` 已删除；剩余索引为 `ra_run_pkey`、`ra_run_session_id_client_request_id_key`、`idx_run_session`。

### 3.3 真实模型双流验证

通过已登录的 HTTP 会话，向同一会话先后发起两条 SSE 请求（第一条约 1 秒后发起第二条），使用本机网关模型：

- A：`clientRequestId=verify2-first`，`queue_seq=15`，`created_at=1793797641222`，`ended_at=1793797646943`，`SUCCEEDED`。
- B：`clientRequestId=verify2-second`，`queue_seq=16`，`created_at=1793797642279`，`ended_at=1793797648790`，`SUCCEEDED`。
- B 的创建时间早于 A 的结束时间，结束时间晚于 A，说明 B 在 A 运行期间已准入并排队，A 结束后才执行。
- 两条流的 SSE 事件顺序均为 `meta(QUEUED)` → `queue(QUEUED)` → `queue(RUNNING)` → `text` → `done(SUCCEEDED)`；B 的 `RUNNING` 出现在 A 结束之后。
- 会话历史按 `queue_seq` 排列为：A 用户消息、A 回答、B 用户消息、B 回答。

### 3.4 验证中发现并修复的问题

首次双流验证时第二条请求没有 SSE 输出，后端日志为 `duplicate key value violates unique constraint "ra_one_active_run"`。确认是 `V008` 的历史唯一索引仍在数据库中；已在 `V011` 增加 `DROP INDEX IF EXISTS ra_one_active_run`，重启后重跑通过。该问题是设计文字与旧库约束不一致，不是前端或调度器问题。

## 4. 未验证与已知边界

1. **浏览器点击验收未执行**：当前环境没有可用的浏览器自动化工具。前端改动由单元测试和构建覆盖，但“页面上连续输入、排队提示、取消按钮”的真实交互仍需用户在浏览器确认。
2. **浏览器同源连接数仍是阻塞项**：每条排队消息占一条 SSE；HTTP/1.1 下单 origin 约 6 条连接，多会话/多标签页仍可能占满并挂起普通 API。每会话上限 2 只是单会话缓解，设计文档第 11 节的 HTTP/2、提交/订阅拆分或单 SSE 复用方案尚未决定。
3. **每会话上限语义**：`max-queued-per-session=2` 实际限制的是活动 run 总数（含 RUNNING），不是“额外排队数”。默认只能运行中再发一条；第三条返回 429。若希望“1 条运行 + 2 条排队”，需把判断改为只统计 QUEUED，或调大该值并同时处理连接数。
4. **WAITING_USER + 排队消息**：后一条会等待前一条回答/取消；未做专门的交互验收。
5. **刷新/断线**：沿用现有语义，SSE 断开取消对应 run；排队中的 run 在刷新后同样会被取消，用户消息文本保留。
6. **重启**：现有 `recover()` 会把遗留 `QUEUED/RUNNING` 标记为 `INTERRUPTED`，不自动重放；本次未新增恢复策略。
7. **多实例**：仍依赖数据库单实例锁与进程内队列，不支持多实例部署。
