# 会话内消息排队设计

> 状态：已实施（2026-11-04），实现与验证见[实现与验证记录](会话消息排队实现与验证记录.md)
> 目标：运行中仍可发送下一条消息；同一会话按发送顺序逐条回答；不同会话保持并行。
> 范围：后端原生队列（非纯前端队列）。
>
> 修订说明：已按评审补充闸门清理、队列顺序、超时语义、乐观消息关联和失败轮次上下文边界。浏览器同源连接数仍是多会话扩展前的阻塞决策，本期以每会话活动 run 上限 2 缓解。

## 1. 目标与非目标

### 目标

1. 助手回答期间输入框保持可用，发送后消息立即进入对话列表。
2. 同一会话内严格串行：前一条运行结束后，下一条才开始；顺序与发送顺序一致。
3. 不同会话不受影响，仍受全局并发/队列上限约束。
4. 排队、运行、取消、等待用户补充都有明确、可查询的状态。
5. 排队消息在服务端落库，刷新后消息文本仍可见（运行本身是否可接续见第 1 节非目标第 2 条）。

### 非目标（本期不做）

1. **消息合并**：“两条消息差不多就一次回答”不在本期。合并只能靠“空闲时延迟几百毫秒再提交”的窗口实现，作为独立小功能另行讨论。
2. **刷新/断线后自动续流**：当前语义是“SSE 连接一断就取消运行”（`ChatApplicationService.disconnected()`）。本期沿用，排队中的 run 在刷新后同样会被取消，但用户消息文本保留。
3. **多实例/分布式队列**：当前一个 schema 只允许一个运行实例，内存队列足够。
4. **跨标签页实时同步**：两个标签页可同时发送，服务端会正确排队，但各自的流互不可见，需要靠刷新查看。

## 2. 现状与限制

### 2.1 已有的能力

| 能力 | 位置 | 说明 |
| --- | --- | --- |
| 全局异步执行 | `run/admission/BoundedRunExecutor.java` | 默认 2 个执行线程 + 8 个等候位 |
| 全局 FIFO 等候区 | `run/dispatch/RunQueue.java` | 单进程 FIFO，只有全局顺序，没有会话维度 |
| 运行落库与排队状态 | `ConversationRepository.beginQueued()`、`TaskStateRepository.enqueue()` | `QUEUED` 状态已存在 |
| 上下文延迟读取 | `ContextPreparationService.bind()` | 历史在任务真正开始时才读取，排队消息能看到前一轮回答 |
| 事件与取消 | `RunQueryController` | 查询事件、取消运行已具备 |

### 2.2 阻止“连续发送”的三处约束

1. **前端单流**：`chatSession.js` 用 `operations: Map<sessionId, op>`，`execute()` 遇到已存在的操作直接返回；`busy` 又用于禁用输入框（`ChatWorkspace.vue`）。
2. **后端同会话互斥**：`ConversationRepository.java` 的 `begin()` 在会话行锁内检查
   `status IN ('CREATED','QUEUED','RUNNING','WAITING_USER')`，存在即返回 `409`。
3. **数据顺序假设**：消息按 `ra_run.created_at, id` 排序；同一毫秒创建的两个 run 顺序由随机 UUID 决定，不能作为严格 FIFO 依据。

### 2.3 为什么不能简单放开 409

`RunQueue` 只保证全局 FIFO。放开 409 后，只要全局还有空槽，同一会话的两个 run 会同时进入 `RUNNING`：

- 两个 run 各自读取历史，可能读到对方尚未完成的中间状态；
- 回答输出与用户消息的归属关系不再唯一；
- `SessionWriteLease` 只保护“创建”事务，不保护整轮运行。

因此需要补的是**按会话串行的闸门**，而不是更多线程。

### 2.4 实施基线（评审补充）

1. 本文引用的 `run/admission`、`run/dispatch`、`run/question`、`run/api` 目录来自**尚未提交**的重构。实施前先把这批重构单独提交并跑通（当前 HEAD 为 `4d1c114`，分支 `Ray/structure-context-rag`），再做本功能。两个大改不要叠在同一个未提交工作区里，否则出问题无法定位、也无法单独回滚。
2. 当前工作区已有一处前端修复：发送时立即清空输入框并在本地插入用户消息（`chatSession.js` 的 `submit()`，配套测试"发送后立即清空输入框并显示用户消息"）。实施 4.7 时以此为起点，**不要回退**成"回答结束后才清空并显示"的旧行为。
3. 验收命令：前端 `cd ray-agent-web && npm test`（当前 34 条全绿）与 `npm run build`；后端 `mvn -q test`；PostgreSQL 集成测试需设置 `RAY_PG_TEST=true`。

## 3. 总体方案

核心思路：**每条消息在准入时立即创建一个 `QUEUED` run 并落库；调度器按会话串行放行；一个会话同时最多一个 run 处于运行或等待用户状态。**

```
浏览器                                    后端
  |-- POST /api/chat/stream M1 ----------->| reserve → beginQueued(R1, seq=1)
  |<-- meta(R1, QUEUED) -------------------| 提交到会话队列
  |<-- queue(R1, QUEUED, position=0) ------|
  |           （R1 取得会话闸门 → RUNNING）
  |-- POST /api/chat/stream M2 ----------->| reserve → beginQueued(R2, seq=2)
  |<-- meta(R2, QUEUED) -------------------| 提交到会话队列，等待闸门
  |<-- queue(R2, QUEUED, position=1) ------|
  |<-- text(R1) ... done(R1) ------------->| R1 终态 → release(session) → wake()
  |<-- queue(R2, RUNNING) -----------------|
  |<-- text(R2) ... done(R2) ------------->|
```

要点：

- 每条消息一个 HTTP/SSE 连接，一个 run；不做“一个连接承载多条消息”。
- 消息文本在准入时写入 `ra_message`，因此普通刷新后仍能在历史里看到。
- 排队的 run 在收到 `meta/queue` 后保持连接（心跳每 2 秒），等轮到自己再开始流式输出。
- 前端不再用 `busy` 禁用输入；`busy` 只用于展示“正在回答/排队中”。

## 4. 详细设计

### 4.1 数据与顺序

新增迁移 `ray-agent-server/src/main/resources/db/migration/V011__session_queue.sql`：

```sql
-- 会话内严格 FIFO 的排序依据；不能依赖同毫秒的 created_at。
CREATE SEQUENCE IF NOT EXISTS ra_run_queue_seq;

ALTER TABLE ra_run ADD COLUMN IF NOT EXISTS queue_seq BIGINT;

-- 旧数据用 row_number 按确定性顺序回填，再将序列推进到最大值。
WITH ordered AS (
    SELECT id, row_number() OVER (ORDER BY created_at, id) AS seq
    FROM ra_run
    WHERE queue_seq IS NULL
)
UPDATE ra_run r
SET queue_seq = ordered.seq
FROM ordered
WHERE r.id = ordered.id;

SELECT setval('ra_run_queue_seq', COALESCE(MAX(queue_seq), 1), COUNT(*) > 0) FROM ra_run;

ALTER TABLE ra_run ALTER COLUMN queue_seq SET NOT NULL;
ALTER TABLE ra_run ALTER COLUMN queue_seq SET DEFAULT nextval('ra_run_queue_seq');
```

需要同时修改 `application.properties` 的 `spring.sql.init.schema-locations`，追加该迁移。

新 run 的 `queue_seq` 统一由数据库默认值 `nextval('ra_run_queue_seq')` 生成，INSERT 不再显式另取一次序列值，避免双重取号。历史数据按 `created_at, id` 确定性回填。

排序统一以 `queue_seq` 为准（消息升序、运行列表降序）：

- `ConversationRepository.messages()`（会话消息列表）
- `ConversationRepository.runs()`（运行列表；现为 `created_at DESC, id`，同毫秒时顺序仍随机，前端会选错当前运行）
- `SessionRebuilder.turns()`（重建成功轮次，模型上下文实际走这里）
- `ConversationRepository.history()` 目前没有任何调用点，一并改掉即可，不算独立改动。

`ra_run` 不增加“每会话唯一活动运行”的数据库约束，因为本次要允许多条 `QUEUED`；互斥由调度器的会话闸门保证。

### 4.2 准入：允许同会话多条 QUEUED

修改 `ConversationRepository.begin()`：

1. 保留会话行锁（`SessionWriteLease`）和幂等检查（`RequestIdempotencyService.assertNew`）。
2. 删除“同会话已有活动运行 → 409”的检查。
3. 增加按会话的活动运行上限检查（新增配置，见第 6 节）：
   ```sql
   SELECT COUNT(*) FROM ra_run
   WHERE session_id=? AND status IN ('CREATED','QUEUED','RUNNING','WAITING_USER')
   ```
   达到上限返回 `429`，提示“该会话排队已满，请等待或取消”。
4. 如果会话当前是 `WAITING_USER`，直接返回 `409`：“等待你补充信息，请先回答或取消”。理由见 4.5。
5. 插入 run 时不传 `queue_seq`，由数据库默认值生成；`ra_message` 的用户消息照旧在同一事务插入。

幂等语义不变：同一 `(session_id, client_request_id)` 仍由唯一约束和 `assertNew` 拦截，重发返回原来的 run。

### 4.3 会话串行闸门

新增 `run/admission/SessionRunGate.java`：

```java
/** 单进程内保证同一会话最多一个运行处于“已提交/运行中/等待用户”状态。 */
@Component
public class SessionRunGate {
    private final Map<String, String> owners = new HashMap<>(); // sessionId -> runId

    public synchronized boolean tryEnter(String session, String run) {
        String owner = owners.get(session);
        if (owner == null) { owners.put(session, run); return true; }
        return owner.equals(run); // 等待用户补充后的续跑沿用同一 runId
    }

    public synchronized void release(String session, String run) {
        owners.remove(session, run);
    }
}
```

接入点：

| 时机 | 动作 |
| --- | --- |
| 调度器选中某个 job 时 | `tryEnter(session, run)`；失败则留在等候区 |
| `ChatRun.end()`（任何终态） | 调用统一的 `executor.finish(session, run, permit, terminalAction)`；先执行并确认数据库终态成功，再 `gate.release`，然后释放 permit 并调度下一任务 |
| `ChatRun.pause()`（WAITING_USER） | **不释放会话闸门**，只释放全局 permit；闸门继续由该 run 持有 |
| 取消 WAITING_USER 的运行 | 数据库终态提交后由统一 executor 协调器释放 gate、释放 permit 状态并唤醒 |
| 等待用户提问过期 | 过期扫描返回 run 后交由统一 executor 协调器释放 gate、释放 permit 状态并唤醒 |
| `QueuedRunDispatcher` 中 `states.start()` 返回 false | `bridge.cancel()` 不会触发 `ChatRun.end()`，必须通过统一 executor 完成路径释放 gate/permit 并唤醒 |
| `BoundedRunExecutor.Job.run()` 因 permit 已关闭而跳过 | 同样不触发 `ChatRun.end()`，必须通过统一 executor 完成路径清理 |
| `workers.execute(job)` 抛 `RejectedExecutionException` | job 可能已从等待队列移除并占用 gate；统一完成路径要将 run 结束为 `INTERRUPTED`/明确失败、移除 running 占位、释放 gate/permit 并继续调度 |
| 取消排队中（尚未 started）的 run | `ChatRun.end()` 调用统一完成路径；若 job 未曾取得闸门则 gate release 为空操作 |

**评审补充：闸门生命周期约束**

1. `release(session, run)` 必须幂等：用 `Map.remove(session, run)` 语义，重复调用不能把后来取得闸门的新 run 踢掉。
2. 释放顺序固定为「数据库终态提交成功 → 释放会话闸门 → 释放全局 permit/running 占位 → 唤醒队列」。先放闸门会让下一条消息读到不含上一轮回答的历史；先 wake 再释放全局槽会造成唤醒无效。
3. 闸门锁是**叶子锁**：持有 gate 锁时不得再申请队列锁或 executor 锁；`release` 返回后再操作队列，避免与 `ready()` 的「队列锁 → 闸门锁」形成反向加锁。
4. 终态、取消、启动失败、job 跳过及执行器拒绝都必须汇入统一 executor 完成路径。路径应幂等，且数据库终态失败时不能提前释放 gate 让后续 run 读取不完整上下文。

`RunQueue` 扩展为“会话感知 FIFO”：

- job 增加 `sessionId`、`runId`、`queueSeq` 元数据。
- `ready()` 从队头扫描等候队列，跳过“会话闸门已被其他 run 占用”的 job，直到全局槽位填满；同一会话内仍保持先进先出。
- 新增 `wake()`，在闸门释放、job 取消后重新执行 `ready()`。
- 闸门占用与 `ready()` 在同一把队列锁内完成，避免并发选到同一会话。

伪代码：

```java
private List<Job> ready() {
    var result = new ArrayList<Job>();
    var it = waiting.iterator();
    while (running.size() < limit && it.hasNext()) {
        Job next = it.next();
        if (!gate.tryEnter(next.sessionId(), next.runId())) continue;
        it.remove();
        running.add(next);
        result.add(next);
    }
    return result;
}
```

`BoundedRunExecutor.Permit.close()` 仍负责释放全局槽位；**会话闸门不由 permit 关闭释放**，这样 `pause()` 不会把会话让给后面的消息。

### 4.4 SSE 与超时

当前 `execute()` 为全局排队设置 `queueTimeoutMs`，启动后换成运行预算。新增 `ray.run.session-queue-timeout-ms=120000` 作为唯一的“准入至真正开始执行”上限；旧 `ray.run.queue-timeout-ms` 不再单独计时，避免两个 queue deadline 竞争。

1. `SseEmitter` 超时改为 `sessionQueueTimeoutMs + Math.max(1, remaining) + 5000`，覆盖会话排队和执行期限。
2. 未开始时 deadline 使用 `sessionQueueTimeoutMs`，原因记为 `QUEUE_TIMEOUT`；`started()` 时取消并换成运行 deadline。
3. 排队等待时限与实际运行时限分开计算：准入时启动 `sessionQueueTimeoutMs` deadline；真正开始执行时取消该 deadline，并启动完整的 `budget.timeoutMs()` 活跃运行 deadline（接续等待提问时仍扣除该 run 之前已消耗的活跃时间）。因此一个请求最多等待 120 秒，再最多执行配置的 60 秒；`SseEmitter` 总超时覆盖两段时间。排队时间不消耗模型活跃运行预算，语义与现有“取得运行槽后才启动活跃超时”一致。
4. `queue` 事件增加 `position`（本会话中排在自己前面的活动 run 数）与 `blockedBy`（`RUNNING`、`WAITING_USER` 或 `GLOBAL_QUEUE`），前端可显示排队位置和阻塞原因。查询：
   ```sql
   SELECT COUNT(*) FROM ra_run
   WHERE session_id=? AND queue_seq < ?
     AND status IN ('CREATED','QUEUED','RUNNING','WAITING_USER')
   ```
   `blockedBy` 由队列调度器根据实际阻塞源产生；数据库计数只提供位置，不能单独推断阻塞源。前端据 `blockedBy` 显示“前一条正在回答”或“前一条在等待你补充信息”，避免用户误以为卡住。
5. **评审补充：定时器拆分**。`timers` 目前是单线程（`ChatApplicationService` 构造器），心跳、运行截止时间和每 30 秒的 `questions.expire()` 共用。排队消息变多后，`expire()` 的数据库查询会拖慢所有会话的心跳，表现为流式输出停顿。实施时把过期扫描放到独立调度器（或至少独立线程），不要与心跳共用。

保留现状：连接断开仍会取消运行（`disconnected()`），包括尚未开始执行的排队 run。这是本期的已知边界，见第 9 节。

### 4.5 等待用户补充（WAITING_USER）

采用“堵住队列”的语义：

- `WAITING_USER` 期间，该 run 继续持有会话闸门，后面的消息保持 `QUEUED`。
- 新的发送请求直接 `409`，提示先回答或取消；补充回答走已有的 `/api/runs/{id}/answers`。
- 用户回答后，`resume()` 用同一 `runId` 重新提交；闸门 `tryEnter` 允许同 run 重入，执行结束后再放行下一条。
- 用户取消或提问过期时，释放闸门并唤醒队列。
- 排队消息自身有 2 分钟排队上限；如果前一条长时间停在等待补充，排队消息会先超时结束，这是可接受的边界。

选择理由：等待补充时，会话的“下一轮上下文”取决于这条回答；放行后续消息会让模型在缺少关键补充的情况下作答，语义不可靠。

### 4.6 取消、重启与恢复

- **取消排队中的 run**：`ChatApplicationService.cancel()` 找到 `active` 中的 `ChatRun` 并 `end("CANCELLED")`；`permit.close()` 把它从全局等候区移除，`end()` 释放闸门并唤醒后续消息。
- **取消运行中的 run**：现有行为不变；终态后放行下一条。
- **取消等待补充的 run**：现有 `questions.cancel()` 之外，将成功提交的取消终态交给统一 executor 协调器释放闸门并唤醒。
- **未进入 ChatRun 终态的路径**：`QueuedRunDispatcher` 在 `states.start()` 返回 false 时走 `bridge.cancel()`，`BoundedRunExecutor.Job.run()` 在 permit 已关闭时直接跳过；执行器拒绝也不会通知下游 `ChatRun`。三条路径统一交由 executor 完成协调器清理 gate/permit/running 占位并唤醒，否则会话可能一直卡到排队超时。
- **启动恢复**：`InterruptedRunRecovery` 现有逻辑会把所有 `CREATED/QUEUED/RUNNING` 标为 `INTERRUPTED`；内存闸门启动时为空，无需重建。排队消息的文本仍在历史中，状态显示“未完成”。
- **等待提问过期**：过期扫描改为返回过期的 `(owner, session, run)` 列表，由统一队列协调器释放闸门并唤醒。过期扫描不再作为无返回值的副作用方法；包括 `consume()` 开头在内的所有调用点都必须处理返回列表，否则可能已把数据库状态改成 `TIMED_OUT`，却遗留 gate 占用。

### 4.7 前端改造

#### Store（`ray-agent-web/src/stores/chatSession.js`）

1. `operations` 从“每会话一个”改为“每个请求一个”：
   ```js
   const operations = shallowReactive(new Map()) // key: clientRequestId / 回答请求键
   const opsOf = sid => [...operations.values()].filter(op => op.sessionId === sid)
   const runningOp = computed(() => opsOf(state.sessionId).find(op => op.view.status === 'RUNNING'))
   const busy = computed(() => opsOf(state.sessionId).length > 0)
   ```
2. `canSend` 去掉 `!busy`、`!active`；保留 `!fetching`、`!creating`、`!error?.uncertain`、渠道已选、草稿非空；增加 `!state.question`（等待补充时按钮由输入框禁用兜底）。
3. `execute()` 去掉 `if (operations.has(sid)) return`，改为按请求键去重。
4. 乐观用户消息以 `clientRequestId` 作为本地关联键：插入时保存 `clientRequestId` 与 `runId: null`；收到 `onMeta` 后按 `clientRequestId` 定位该消息并补写 `runId`。排队状态、取消按钮、助手回答都按 `runId` 关联；不能用数组最后一项推断对应消息。服务端刷新后按 `runId` 合并/替换本地消息，避免重复显示。
5. `onMeta`：只登记 `op.runId`；**只有当前没有其他 `RUNNING` 操作时**才更新 `state.currentRun` 和轨迹面板，避免排队消息的 meta 抢走正在输出的运行视图。
6. `onQueue`：更新该 op 的状态；会话级 `state.status` 只由“当前 running 的 op”或“没有 running 时的第一条排队消息”写入。
7. `liveAnswer`：只取 `runningOp` 的文本；没有 running 时返回空，避免把多条回答拼在一起。
8. `finally` 刷新保持不变（已有 `refreshId/token` 防竞态）；每条 op 结束都会刷新，最终消息以服务端为准。
9. 失败处理：
   - 当前 running/可见 op 失败 → 仍写 `state.error`，并把问题放回输入框（沿用现有逻辑）。
   - 排队 op 被取消/超时 → 不覆盖其他 op 的状态，只通过该消息对应的 run 状态展示。
10. `cancel()`：默认取消当前 `RUNNING` 的 run；排队消息在界面上单独提供“取消排队”，调用同一 `/api/runs/{id}/cancel`。
11. `dispose()`：中止所有 op。
12. **`refresh()`、`active` 与 `runs()` 排序**：
    - `refresh()` 现在无条件 `state.currentRun = runs.find(...) || runs[0]`，而每个 op 的 `finally` 都会 refresh。改为：存在 `RUNNING` 的 op 时保留其 `currentRun`，不被 `runs[0]` 覆盖。
    - `active` 现在取 `state.runs` 里第一条 `ACTIVE`。改为优先取 `RUNNING`，没有正在运行的再取队首 `QUEUED`；状态栏、“停止”按钮和轮询都依赖它。
    - `state.runs` 的服务端排序同步改为 `queue_seq DESC`（见 4.1），否则同毫秒创建的排队消息在刷新后顺序不稳定。
13. **恢复凭据按请求存**：`notices` 和 `state.pending` 目前是会话级单值，第二条消息一发就覆盖第一条。改为以 `clientRequestId` 为键存 Map；失败时恢复/查询必须绑定到对应 run，不能跨请求覆盖。

#### 页面（`ray-agent-web/src/pages/ChatWorkspace.vue`）

1. 输入框 `:disabled` 去掉 `chat.busy.value` 和 `chat.active.value`，保留 `s.creating`、`s.fetching`、`s.error?.uncertain`、`state.question`。
2. 消息列表按 `runId` 关联 `state.runs`：用户消息在 `QUEUED` 时显示“排队中”，`RUNNING` 时显示“正在回答”，终态失败显示“未完成”。
3. 顶部/输入框附近显示“已排队 N 条”提示（N = 本会话 `QUEUED` run 数）。
4. 排队消息的取消入口：消息行上的“取消排队”按钮。
5. 发送按钮的可用性完全由 `canSend` 决定。

## 5. 状态流转

```
准入 → QUEUED（等待全局槽位 / 会话闸门）
     → RUNNING ──→ SUCCEEDED / FAILED / CANCELLED / TIMED_OUT / INTERRUPTED
              └──→ WAITING_USER（保持会话闸门）
                       ├─ 回答 → 续跑（同一 runId）→ RUNNING → 终态
                       ├─ 取消 → CANCELLED → 放行下一条
                       └─ 过期 → TIMED_OUT → 放行下一条
```

## 6. 新增配置

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `ray.run.max-queued-per-session` | **`2`** | 每会话活动 run 上限（含 QUEUED/RUNNING/WAITING_USER） |
| `ray.run.session-queue-timeout-ms` | **`120000`** | 从准入到开始执行的最大等待，超时 `TIMED_OUT/QUEUE_TIMEOUT` |
| `ray.run.queue-timeout-ms` | 移除/停止使用 | 由唯一的 `ray.run.session-queue-timeout-ms` 统一限制准入到开始执行的总排队时间 |

**连接数限制说明（修订）**：每条排队消息占一条 SSE。浏览器 HTTP/1.1 的同源连接上限是按浏览器源计算，不是按会话计算；一个会话最多 2 条并不能限制多个会话/标签页的总 SSE 数。当前全局准入上限默认可达 10 个运行（2 running + 8 queued），因此仍可能占满浏览器对 `localhost:5173` 或 `127.0.0.1:8080` 的连接槽。实施前必须解决：选择启用并验证 HTTP/2，或将“提交运行”和“订阅事件”拆成独立 API（排队期间不长期占用 SSE），或采用一个会话复用单 SSE 的协议。不能把每会话上限 2 当作充分保护；该项列为实现前阻塞决策，见第 11 节。

### 后端单元

1. `RunQueue`：A1、A2、B1 入队且 A1 运行中时，B1 可执行，A2 必须等 A1 终态；A1 结束后 A2 按序执行。

4. **闸门不泄漏**：`states.start()` 返回 false、permit 在 `Job.run()` 前被关闭、取消尚未 started 的排队 run、`workers.execute(job)` 被拒绝，四种情况都必须清理 running/gate/permit 并唤醒后续消息。
5. **上下文顺序**：A1 成功后 A2 才开始，且 A2 能看到 A1 的问答；A1 在 `WAITING_USER` 时 A2、A3 都不放行。

### 后端集成（PostgreSQL + 模拟模型）

1. 同会话连续两条消息：第二条 `QUEUED`，第一条结束后第二条才 `RUNNING`；第二条上下文包含第一轮问答。
2. 不同会话并行：两个会话各一条消息，可同时 `RUNNING`（全局 2 槽）。
3. 取消排队消息：从未执行，终态 `CANCELLED`，用户消息仍在历史中。
4. 取消运行中消息：下一条自动开始。

6. 排队超时：前一条运行超过 `session-queue-timeout-ms`，后一条按 `QUEUE_TIMEOUT` 结束。
7. 重启：`QUEUED` 全部标为 `INTERRUPTED`，用户消息保留。
8. 幂等：相同 `clientRequestId` 重发不产生第二个 run。
9. **恢复顺序**：A1 等待补充，用户回答后 A1 续跑先于 A2；A1 结束后 A2 才开始。
10. **失败轮次**：A1 失败后 A2 仍能开始，不因 A1 终态卡住；按现有语义，A2 的模型上下文不含失败的 A1 用户提问，前端提示上一条未完成。

2. 切换会话时多个流的文本/事件不串台。

## 9. 已知边界与风险

1. **刷新会取消排队中的 run**：SSE 一断即 `disconnected()`。要解决需要把“运行执行”与“SSE 输出”解耦，属于下一阶段（可按 runId 重新订阅或后台执行 + 事件补齐）。本期不扩大范围。
2. **等待补充可能让排队消息超时**：前一条停 2 分钟以上未回答时，后一条会先 `QUEUE_TIMEOUT`。前端必须显示“前一条在等待你补充信息”，而不是只显示排队位置。
3. **内存闸门不跨重启**：重启后所有活动运行被标中断，闸门清空，与现有恢复语义一致。
4. **多标签页**：服务端排队正确，但各标签页只看到自己的流；需要刷新对齐。
5. **取消与新建的竞态**：前端取消排队消息后立即重发，仍由 `clientRequestId` 幂等兜底。
6. **前端状态归属**：多条流共用会话级 `status/error` 时容易互相覆盖，实施时必须按 4.7 的“只有 running op 写会话级状态”约束，并补测试。
7. **浏览器同源连接数**：每条排队消息占一条 SSE，HTTP/1.1 下同源约 6 条；因此每会话上限默认 2。超限的表现为普通 API 请求被挂起、界面像卡死，而不是报错。启用 HTTP/2 或改为按 runId 复用单流后才可放宽。
8. **前一条失败时后一条缺少该提问**：`SessionRebuilder.turns()` 只投影 `SUCCEEDED` 轮次。排队后连发 M1、M2 且 M1 失败时，M2 的上下文不含 M1。本期保持现有上下文语义，前端提示“上一条未完成”；后续如需纳入失败用户消息，另行评审。
9. **单线程调度器**：心跳、截止时间与 `expire()` 共用 `timers`；排队消息增多后数据库查询会拖慢心跳。按 4.4 第 5 条拆分。
